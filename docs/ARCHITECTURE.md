# Architecture

`grad` is a standalone, self-hostable training platform designed around one authoritative OpenAPI 3.1 contract (`spec/openapi.yaml`) and strict self-hosted / Cloud parity.

## Components

1. **Control Plane (`server/api/`)**: TypeScript + Hono (`@hono/zod-openapi`), PostgreSQL 17 + S3-compatible storage (AWS S3, SeaweedFS, MinIO, R2). Zero Valkey, ClickHouse, or Temporal dependencies in self-hosted mode, and no in-process state that breaks with several API replicas.
   - **Routes** (`src/routes/`) are thin: user routes for datasets/imports/uploads, runs, checkpoints, artifacts (including artifact uploads and imports, `/v1/artifact-imports`, deletes and the internal pins), evals, keys and the usage ledger (`GET /v1/usage`, and `GET /v1/usage/summary`, which aggregates a period in SQL); `trainer-jobs.ts` is the worker protocol. Deploying, routing, embeddings and feedback are Gradiated Cloud's inference API, so grad-server has no routes for them. A global error handler renders every error (unknown route, malformed JSON, validation, thrown) as `application/problem+json` with a `request_id`. List endpoints share `?limit&cursor` → `{data, next_cursor}` keyset pagination.
   - **Settings** (`src/deps.ts`): `DEFAULT_SETTINGS` holds every setting's default once; `resolveSettings` applies them, and `environment.ts` defaults its variables from the same table, so services read `deps.settings.x` with no fallback of their own.
   - **HTTP limits** (`src/app.ts`, `src/http-guards.ts`): JSON bodies are capped at 32 MiB (`413 payload_too_large`; files go through upload tickets), and each replica handles at most two bodies over 1 MiB at once, the rest waiting their turn, because a parsed push costs about ten times its size in heap.
   - **Services** (`src/services/`) own business rules and transactions: `jobs.ts` (the one queue: claim, heartbeat, lease expiry and the attempt rule for train, import and eval jobs), `runs.ts` (run lifecycle, budgets, the train side of the worker protocol), `run-plan.ts` (resolving a recipe into a plan), `checkpoints.ts` (retention, best/final pins, promotion), `artifacts.ts` (the registry: deletes and pins), `sources.ts` (source syncs), `secrets.ts` (workspace secrets: sealed at rest, revealed only to a host they allow), `imports.ts`, `datasets.ts` (a version is read a page at a time through its merge index, which a dataset's next version extends with only its new parts; a run plan reads at most 100k records spread over the version and scales its counts), `uploads.ts` (content-addressed keys, no upload rows), `usage.ts` (incremental usage ledger and the Cloud exporter), `evals/` (eval planning, pricing, aggregation and results; no model calls) and `maintenance.ts` (lease expiry, checkpoint expiry, staged-upload and job-event sweeps, usage export).
   - **Store** (`src/store/`): per-resource repository interfaces (`types.ts`) implemented on Postgres (`postgres/`) and verified by `test/store-contract.test.ts`. Seventeen tables, created by the versioned migrations in `migrations/` (`0001_initial.sql` to `0011_scale_indexes.sql`): `grad_api_keys`, `grad_datasets`, `grad_dataset_parts`, `grad_sources`, `grad_secrets`, `grad_jobs`, `grad_job_events`, `grad_workers`, `grad_worker_tokens`, `grad_runs`, `grad_evals`, `grad_eval_outputs`, `grad_artifacts` (checkpoints and releases), `grad_artifact_pins`, `grad_usage`, `grad_usage_export` and `grad_workspace_states`. Create endpoints store the caller's Idempotency-Key and a request hash on the row they create. Tests run on a real Postgres too: one schema per test file, emptied per test. `store.transaction(fn)` gives atomic multi-repository writes: the transaction is ambient, so every store call inside `fn` joins it (nested calls take a savepoint); migrations are versioned (`grad_schema_migrations`) under an advisory lock.
   - **Storage** (`src/storage/`): `ObjectStore`, implemented on S3 only (`s3.ts`; there is no local-disk mode, and `grad local up`, the test harness and CI run SeaweedFS). Keys are content-addressed (`ws/<ws>/jobs/<job>/<attempt>/<sha256>`, `ws/<ws>/datasets/<dataset>/<sha256>.jsonl.gz`, staged imports under `uploads/<ws>/<sha256>`); presigned PUTs bind Content-Length and `x-amz-checksum-sha256`, and committing an upload checks its sha256 on any backend (HEAD's checksum, else a streamed hash). `S3_PUBLIC_ENDPOINT` signs client upload tickets for the address SDK clients reach.
   - **Event streams**: the SSE endpoint (`GET /v1/runs/{id}/events` with `Accept: text/event-stream`; metric points are its `metric` events) reads from `services/event-hub.ts`, one reader per replica for all its streams. It LISTENs on `grad_job_events` (migration 0004's triggers NOTIFY the job id on every event insert and every job status or worker change), fetches new events for the notified jobs in one bounded query (`job_id`/cursor pairs, at most 500 rows per job), and re-reads every followed job every `SSE_POLL_MS` in case a notification was missed. Postgres stays the source of truth, so a stream on any replica sees events written through any other. Streams backfill from `Last-Event-ID` (or the start), ping when idle and end on SIGTERM so clients resume elsewhere.
   - **Adapters** (`adapters.ts`, and `src/cloud/` for Cloud mode) for Auth and Billing (tested against `test/fixtures/fake-cloud-api.ts`). The artifact registry is grad's boundary with serving: released bundles live under one content-addressed `artifacts/` prefix that Gradiated Cloud reads directly, and publishing a model version pins its artifact (`grad_artifact_pins`, `ON DELETE RESTRICT`) so grad never deletes it.
   - **Worker authentication** (`worker-auth/`): a worker's bearer token resolves to a worker principal (kinds, identity, and for lease tokens host, lease, GPU bound and expiry) through the authenticators in `GRAD_WORKER_AUTH`, in order: `static` (`TRAINER_KEYS_JSON`, constant-time), `kubernetes` (projected service-account tokens checked with the TokenReview API, the account mapped to kinds; only JWTs whose unverified claims name audience `grad`, a mapped account and a future `exp` are reviewed, at most 8 at once per replica; positive reviews cached for at most 60 s and never past the token's `exp`; while the API is down or busy a token reviewed in the last 15 min keeps working, anything else gets a 503) and `lease` (`gradwt_` tokens an orchestrator mints on the internal listener `INTERNAL_PORT`, `routes/internal.ts`; only their SHA-256 is stored, in `grad_worker_tokens`, and each is bound to a host, kinds, a GPU bound and an expiry). The principal's identity (for lease tokens `lease:<orchestrator>/<host>/<lease>`) becomes the lease fence (`worker_key`), so one credential can never touch another's lease or read its dataset; `worker_key` outlives the attempt, so a retried `/complete` is answered only for the credential that closed it. Workers read `GRAD_WORKER_TOKEN` or `GRAD_WORKER_TOKEN_FILE` (re-read per request).
   - **Trainer protocol v1** (`/v1/trainer-jobs/*`, platform scope `trainer:worker`, never implied by `admin`): `claim` (train | import | eval jobs; pinned dataset version, resume checkpoint, remaining budget; an eval's targets, rubric and the outputs earlier attempts stored), background `heartbeat`, `progress`, `uploads` (presigned or signed PUT: bundles, and an import's dataset parts), `checkpoints`, `parts` (an import worker uploads gzip JSONL parts of ~50k records or 64 MB straight to storage and registers each by `(job, attempt, seq)`; grad-server checks the object and never reads the records), `outputs` (eval jobs: batches of generated and scored outputs, stored once per `(eval, model, task, sample)`, priced by the server at plan-time prices and billed as they land), `complete` (one transaction: artifact + run + usage row; a status the job's kind doesn't have is refused with 422 `unsupported_completion` before anything changes: a train attempt ends as completed, stopped_budget, failed or abandoned, an eval or import attempt as completed, failed or abandoned, and a job the user cancelled closes as cancelled whatever its worker reports; cost = tokens × catalog price; an eval's completion aggregates it, or waits in `awaiting_scores` for SDK-posted scores). Usage is billed in increments while an attempt runs (every 1M tokens or 5 minutes, at checkpoints, and at the end); on Cloud a heartbeat stops a run whose workspace ran out of balance (`insufficient_balance` → `stopped_balance`, resumable after a top-up; a run at its own `max_cost_usd` is `stopped_budget` and resumes only with a higher cap; the worker reports which on `complete` as `stop_reason`). Claims are fair across workspaces: a GPU worker first takes runs no smaller online GPU fits, then the workspace with the fewest running jobs of the kind (below `GRAD_MAX_RUNNING_PER_WORKSPACE_*`) goes next, then its oldest job the worker fits (a GPU worker's `gpu.memory_gb` against the run's `min_gpu_memory_gb`), in one statement under a per-kind advisory lock with SKIP LOCKED (a poll that would claim nothing, every queued job capped or too big, is answered by the same pick read without the lock, and a replica's claims of a kind queue in process, so lock waiters hold one pool connection); `GRAD_MAX_QUEUED_PER_WORKSPACE` caps queued jobs (429 `queue_limit`). A claim retried by the same worker returns its own job; worker writes are stored once per `(job, attempt, seq|step)`. Expired leases and abandoned attempts requeue as `attempt + 1` until `MAX_ATTEMPTS` of them have happened; preemptions have their own cap, `MAX_PREEMPTIONS` reclaims in a row that saved no checkpoint. KEDA autoscales workers on grad-server's queue metrics (queued + running jobs), through Prometheus or grad-server's metrics API.
   - **Evals** (and `dataset.score()`, router labelling, distillation's teacher answers, checkpoint evals) are `eval` jobs on the queue. The API plans them, creates the job, prices and bills posted outputs, aggregates and serves results; it makes no model calls, so API memory, connections and deploys never touch a running eval. **Eval workers** (`src/worker/`, `node dist/main.js worker --kinds eval` from the grad-server image: the `import` pool in Helm, `grad-eval-worker` in compose) claim them over the trainer protocol and call the OpenAI-compatible endpoint (`GRAD_INFERENCE_BASE_URL`, judges on `GRAD_JUDGE_BASE_URL`); validators, regexes (a worker thread with a hard timeout), judge prompts and task building are the same TypeScript modules the API plans with, so there is one implementation of each. Python function scorers run in the SDK (`awaiting_scores`). Nothing is simulated: without `GRAD_INFERENCE_BASE_URL` on the API, evals return `501 inference_unavailable`.
2. **Training Runtime & Connectors (`server/trainer/`)**: Python `grad-trainer`. `grad_trainer/worker.py` is the protocol-v1 client (heartbeat thread, streaming bundle uploads, graceful SIGTERM, backoff, clear exit on a rejected key) and calls recipes through the seam types in `grad_trainer/runner_types.py`. Recipes implement all 8 v0 recipes (`sft`, `dpo`, `router`, `decision`, `cartridge`, `embedding`, `distill`, `reward`), `gradiated.cartridge/1` safetensors export, deterministic SHA-256 `.grad.tar.gz` bundles, and 9 trace connectors (the file formats `grad_trajectories`, `openai_chat` and `otel`, and the providers `gradiated`, `langfuse`, `posthog`, `braintrust`, `langsmith` and `phoenix`).
3. **OpenAPI 3.1 Codegen (`scripts/generate-sdks.mjs`)**: Deterministic generator emitting zero-drift wire clients for TypeScript, Python, Go, and Rust (`--check` enforced in CI).
4. **4 Idiomatic SDKs (`sdks/{python,typescript,go,rust}`)**: Thin façades over the generated clients with fail-closed SHA-256 artifact verification.
5. **Rust CLI (`cli/`)**: Single binary `grad` built on `grad-sdk`.
6. **Packaging (`server/docker-compose.yml`, `server/helm/grad/`)**: Local Docker Compose stack (`grad local up`: one API, one trainer worker, one eval worker; `--dev-models` adds `grad-dev-inference`, a CPU OpenAI-compatible endpoint for the tiny test models, so evals run locally) and production Kubernetes Helm chart with optional KEDA scale-to-zero and air-gapped model/judge overrides.

## Failure modes

grad's recovery model is at-least-once with idempotent handlers: every worker write has a natural key (`(job, attempt, seq|step)`), every create stores its Idempotency-Key in the transaction that creates the row, attempts are fenced by `attempt` plus the credential's identity (`worker_key`), lease times come from the database clock, and an interrupted attempt replays from its last checkpoint (or, for evals, after its stored outputs). API replicas hold no state that matters: every coordination point is a Postgres row, lock or `SKIP LOCKED` claim, so any replica can die and any other picks up. `test/chaos-*.test.ts` (server) and `server/trainer/tests/test_*chaos_live.py` (real workers, two replicas, a lossy proxy and `kill -9`) exercise each row below.

| Dependency or failure | What breaks | How it recovers |
| --- | --- | --- |
| Postgres restarts or resets connections | In-flight requests get `503 database_unavailable` (`Retry-After: 1`). | Broken clients are destroyed, never returned to the pool. Workers retry; a lease survives an outage shorter than a third of its length (lease + lease/3 before the reaper requeues). |
| Postgres connection black-holed (failover without a reset) | Queries on that connection hang. | They fail after 35 s (client-side timeout; TCP keepalive from 10 s) and the connection is dropped. The SSE hub pings its LISTEN connection every 30 s and reconnects; streams fall back to the 2 s re-read meanwhile, so no event is lost. |
| Postgres long-running transaction elsewhere on the cluster | The Cloud usage export waits (it never skips a row behind an open transaction). | Exports resume when it ends; grad's own sessions are capped by `idle_in_transaction_session_timeout`. |
| Postgres unreachable or DNS failing while the migrations Job runs or a replica boots | Nothing. | `migrate` and the boot check retry for 120 s (`EAI_AGAIN`, refused connections, 57P0x) before failing, so a short outage doesn't fail the rollout or crash-loop replicas into minutes of backoff. During requests the same errors answer `503 database_unavailable`. |
| Migrations started by several pods | Nothing. | Pods serialize on the migration advisory lock, outside the serving pool's statement timeout: one applies, the others find nothing to do. |
| A migration's DDL waiting behind a long query of a live replica | Nothing: queries on that table are queued behind it for at most 5 s. | Each DDL waits at most `lock_timeout` (5 s), rolls back and retries with backoff (12 tries), then fails the Job naming the migration; rerun it once the long transaction ends. A migration not yet released may only expand the schema (no `DROP`, `RENAME`, type change or `SET NOT NULL` without a `-- contract: why` comment, checked by `test/migrations.test.ts`), because the previous release keeps serving on the new schema during the rollout and is what a rollback runs. |
| Rolling upgrade, node drain or pod eviction of an API replica | Nothing. | On SIGTERM `/health/ready` answers 503 while the replica keeps serving for `SHUTDOWN_DRAIN_SECONDS` (Helm: 5), so endpoints drop it first; then SSE streams end (clients resume elsewhere with `Last-Event-ID`) and open requests get 5 s. The chart surges a replica before stopping one and keeps one up through drains (PodDisruptionBudget). |
| S3 down or answering 5xx | Uploads, commits and downloads get `503 storage_unavailable` (`Retry-After: 1`); maintenance's storage steps log and skip. | Clients and SDKs retry. Nothing is half-written: keys are content-addressed and the database commits after the object exists. |
| S3 slow | A request waits at most 120 s for a first byte; a stream at most 120 s between chunks. | Bounded, so no request or DB connection hangs. |
| Storage, KMS or the database failing while a claimed run or import is built | That attempt (nothing ran). | The job requeues, spending the attempt (`max_attempts`), and the claim answers 5xx so the worker backs off before it claims again. An error about the job itself (its dataset version, source or secret gone) fails it at once. |
| An API replica killed mid-request | Its in-flight requests. | Keyed creates replay to the same row; natural-key and state-guarded writes (promote, cancel, sync, worker routes) are no-ops on retry. A retried DELETE answers 404 for something already deleted. SSE clients resume with `Last-Event-ID` on another replica. |
| Maintenance on N replicas at once | Nothing. | Every step is guarded (compare-and-set, `SKIP LOCKED`, a lease or an advisory lock), and one failing step never stops the others. |
| One scheduled source failing | That source's sync. | It runs in its own savepoint and is rescheduled; the others still start (up to 1,000 per tick). |
| Trainer worker `kill -9` or host loss | Work since the last checkpoint. | The lease expires, the job requeues as `attempt + 1` and resumes from the checkpoint; billing chains per attempt, so no token is billed twice. A restarted worker removes the job directories a killed one left. |
| Worker SIGTERM or a spot notice | The attempt. | It saves a checkpoint if one fits `GRAD_RECLAIM_GRACE_SECONDS` and hands back at the deadline at the latest; it requeues at once as a preemption. `MAX_PREEMPTIONS` counts only reclaims in a row that saved no checkpoint, so a long run on spot capacity is never failed for being preempted. |
| Two workers with one `GRAD_WORKER_ID`, or a skewed worker clock | Nothing. | Ids get a per-process suffix, leases are fenced by worker id plus credential identity, and lease times use the database clock. |
| Kubernetes API (TokenReview) down or saturated | New worker tokens get `503 worker_auth_unavailable`. | A token reviewed in the last 15 min keeps working (never past its `exp`; rejections are never cached), so leases ride out short outages; concurrent reviews of one token are merged. |
| Lease token revoked or expired mid-job | The worker gets 401 and stops; an eval is never marked failed for it. | The lease expires and the job requeues, counted toward `MAX_ATTEMPTS`. Drain the worker first (SIGTERM) to hand back as a preemption instead. |
| Worker token file rotated | One 401. | Trainer and eval workers re-read the file and retry once. |
| Import worker killed (download, validate, upload, finalize) | That attempt. | The next attempt redoes it; content-addressed parts and bundles plus the fenced `/complete` give one release, and a retried `/complete` returns it. |
| An artifact delete or the orphan sweep racing a new release of the same bytes | At most the racing release: it copies again (promote) or gets `409 upload_incomplete` and re-uploads on its next attempt. | Deleters take the bundle's advisory lock exclusively and re-check references before deleting; writers hold it shared while they check the object and commit. A release never points at a deleted bundle. |
| A pin racing a delete or a workspace purge | The pin: `404`. | The caller re-resolves. A pinned artifact is never deleted (`ON DELETE RESTRICT`). |
| Workspace purge interrupted (crash, S3 error) | The purge pauses. | It resumes after 60 s on error or after its 300 s lease if the replica died; every step is idempotent and pinned bundles stay. |
| Noisy workspace, mixed GPU sizes | Nothing starves. | Fair share by running count, per-workspace running caps, an exact `queue_limit` across replicas, and GPU workers serve the runs only they fit before small runs. |
| Cloud auth view (product DB) unreachable | Unseen API keys get `503 auth_unavailable`; a key answered before keeps its last answer for up to 5 min (never past its `expires_at`). Console JWTs and workers are unaffected. | The first lookup after the view is back refreshes the answer and applies revocations; past 5 min down, keys fail closed. |
| JWKS unreachable or rotated | Nothing while keys are cached (refreshes run in the background and keep the old keys on failure). With no keys yet (fresh boot), console JWTs get 503. | The next refresh (10 min), or the unknown-`kid` refetch (at most every 30 s): a rotated key verifies on first use. |
| Cloud price list down | Up to 24 h, nothing: the last good list is kept in memory. After that, or on a replica booted during the outage, new runs, evals, plans and `/v1/base-models` get `503 billing_unavailable`. | Polled every 5 min (30 s while there is no list); running work bills at its pinned price version. |
| Cloud balance check down | Creates, resumes and evals get `503 billing_unavailable` (safe to retry with the same Idempotency-Key). Heartbeats keep training. | The next create or heartbeat; one check per workspace in flight, cached 30 s. |
| Cloud usage ingest down for hours | Rows wait in `grad_usage`; lag and backlog metrics grow and balances aren't debited meanwhile. | Backoff 15 s to 5 min, retried forever, then 10k rows per tick. Pushes are idempotent per row (`event_id`), so a lost ack or replay is free. |
| Cloud usage ingest refuses every row without naming one (an envelope or contract break) | Nothing is parked: after 20 unnamed single-row refusals in a tick the export stops narrowing, logs an error and counts a failure on `grad_usage_export_failures_total`. | Treated like ingest down: backoff 15 s to 5 min and retried; `GradUsagePushLagging` fires while the lag grows. |
| Cloud usage ingest refuses a row for good (422/409) | That row only: it is parked (`parked_code`, `parked_at`) and not billed. | The rest export at once. `grad_usage_parked_rows` and the `GradUsageRowsParked` warning alert flag it; parked rows are never deleted and are retried by hand once the cause is fixed (CLOUD_MODE.md). |
| Inference endpoint or gateway down during an eval | Calls wait and retry in place while the worker keeps its lease; no error output or zero judge score is stored; the eval shows `waiting_reason: inference_unavailable`. | It continues when the endpoint answers. After 10 min down the attempt is handed back (counted toward `MAX_ATTEMPTS`) and the next resumes after the stored outputs. |
| No capacity for an eval's model (`503 capacity_unavailable`, a cold pool) or a full eval lane (429) | The call sleeps the `Retry-After` and retries, keeping the lease and the attempt; the eval shows `waiting_reason: capacity_unavailable` or `rate_limited`. | It continues once there is room. Past `GRAD_EVAL_CAPACITY_WAIT_SECONDS` (12 min) the eval fails once with that reason; no attempt is spent on it. |
| Cloud eval-versions call slow or failing | An eval create of a large artifact can take minutes (the product copies the bundle once). | 10 min budget with retries of 5xx/unreachable (idempotent per workspace and artifact); 404/409/422 are `422 artifact_not_servable`, never retried. |

## Locked v0 Scope
- **8 v0 Recipes:** `sft`, `dpo`, `router`, `decision`, `cartridge`, `embedding`, `distill`, `reward` (a forward-compatible typed contract is retained for Wave 2 `grpo`).
- **Parameter-Efficient LLMs Only:** `LoRA`, `PrefixKV`, `FrozenHead` (no `adapters.Full()` for LLMs; `EmbeddingRecipe` trains the 33M `baai/bge-small-en-v1.5` encoder internally).
- **One artifact registry:** trained artifacts, uploads (`grad artifacts upload`) and Hugging Face imports (`grad artifacts import hf://...`) are the same `name@YYYY-MM-DD-n` releases, validated against [ARTIFACT_FORMATS.md](ARTIFACT_FORMATS.md) and carrying their `provenance`. Serving is not grad's: Gradiated Cloud publishes artifacts as model versions through its Models API and pins them; self-hosted users download and serve them.
- **Environments are post-v0:** `grad env serve` (outbound environment workers) and environment evals return in Wave 2, rebuilt on the Postgres job queue.
